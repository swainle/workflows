## AI-TEST-005

- **Who**：处理 `<组件 test>` 指令的组件测试 Agent。
- **When**：任务范围明确后，在形成方案或结束任务前检查适用的专业风险时。
- **Where**：当前组件测试目录与允许读取的设计和源码。
- **What**：提供“评审视角”功能；具体规则、格式和约束如下。
- **Why**：确保组件测试与稳定用例编号、测试层级和文件边界一致。

按当前测试任务逐项检查适用视角：

- 需求追溯：用例是否直接对应有效 `Design`、`Src` 及适用的 BP、BR、FR、AC。
- 测试层级：行为是否位于最低且足够真实的层级，组件边界与全局验收边界是否清楚。
- 失败检测：断言能否识别真实回归，并覆盖正常、失败、边界、权限和关键副作用。
- 稳定性：时间、随机、并发、外部依赖和 Fixture 生命周期是否确定且可重复。
- 风险：安全、性能、事务或兼容性风险是否在实际适用时获得对应测试。

不适用的视角可跳过；发现必须修正于测试代码或在最终回复中列为阻塞，不生成独立评审报告。

## AI-TEST-006

- **Who**：处理 `<组件 test>` 指令的组件测试 Agent。
- **When**：创建、修改、执行或审查组件测试及其 Fixture、支持代码和配置时。
- **Where**：当前组件测试目录与允许读取的设计和源码。
- **What**：提供“测试代码规则”功能；具体规则、格式和约束如下。
- **Why**：确保组件测试与稳定用例编号、测试层级和文件边界一致。

- 开始实现前读取组件 `testing.md` 开头的语言与工具链说明以及“测试命令”和“局部执行”章节，
  并核对组件实际构建、包管理和测试配置，以确定测试框架、目录和用户可手动执行的命令。
- JavaScript 和 TypeScript 组件没有既有测试工具链时默认采用 `pnpm` 和 Vitest；
  项目已有有效工具链时沿用现状，不为统一格式迁移测试框架或包管理器。
- 只使用项目真实存在的分层和局部测试命令；JavaScript 和 TypeScript 组件优先使用实际
  `package.json` scripts，其他语言使用其现有构建或测试入口。
- 需要修改包清单、构建文件、测试运行器根级配置或其他不在 `test/**` 内的运行配置时，
  停止对应部分并说明应切换到 `<组件 dev>`；不得在测试阶段创建替代配置。
- 先通过阅读生产代码、测试代码、类型定义和配置完成静态检查，再按 `testing.md` 记录的真实命令
  执行本次受影响测试；受影响测试通过后执行当前组件全部测试。不得把只运行局部测试写成全部测试通过。
- 覆盖率、Lint、构建和其他非测试验证不默认执行；测试命令自身按项目既有配置触发的前置步骤不属于越权。
- 将 `testing.md` 中每个三级标题定义的稳定测试用例作为测试代码规划依据；测试代码中的
  用例描述必须由三级标题的用例编号和该用例的 `Desc` 组成，并按对应 `Given`、`When`、
  `Then` 实现。
- 用例编号中的测试层级缩写必须与二级标题匹配：单元测试使用 `DOM`、`APP` 或 `INF`，
  集成测试使用 `API` 或 `INT`，其余分别使用 `CON`、`CONC` 或 `E2E`。
- 用例编号必须符合 `component.md` 的对象或能力命名规则；不符合时切换 `<组件>` 修正设计，
  不在测试实现阶段擅自改号。
- 任务要求实现 Requirement TC、启动或断言多个组件或验收跨组件 BP 时，停止对应部分并说明
  应切换全局 `<test>`；组件 E2E 只覆盖当前组件边界内的完整公开入口。
- 实现前验证必填的 `Design`、`Src` 以及可选的 `BP`、`BR`、`FR`、`AC` 实际存在且类型正确；
  `Src` 必须与 `component.md` 完整文件树中的精确测试文件路径一致，并指向该用例计划或实际所在文件；
  这些可选引用只表示当前测试直接验证的内容，不根据上游关系自动展开。引用之间不一致时停止
  并说明应返回对应设计阶段修正。
- 测试实现阶段不得自行选择替代路径、移动或重命名 `Src`；路径缺失、冲突或不符合项目测试文件
  命名约定时切换 `<组件>` 同步修正 `testing.md` 和 `component.md`。
- 一个测试只实现一个主要行为；设计中把不同公开操作、成功与失败分支或独立边界场景合并在
  同一个 GWT 时停止对应部分，并说明应切换 `<组件>` 拆分测试设计。
- 接口测试代码放入 `test/integration/api/`，按实际协议使用 `http/`、`events/` 或
  `rpc/` 子目录，并引用稳定的 OpenAPI `operationId`、AsyncAPI operation 或 RPC 方法。
- 测试必须导入真实生产模块，或通过真实的 HTTP、UI、消息、数据库等公开入口执行生产代码。
- 不得在测试文件中重新实现、复制或简化待验证的业务规则，再对测试中的实现进行断言。
- 测试辅助代码只能构造数据、创建 fixture、替换外部依赖和收集结果，不得决定业务结果。
- 如果生产代码缺少实现、公开入口或可替换依赖，停止对应测试并说明应切换
  `<组件 dev>`；不得在测试中补写替代实现。
- `describe`、`it`、场景名称和必要注释使用中文，清楚说明前置条件、行为和期望结果；
  文件名、变量、函数、类型和导入名称遵循项目代码规范，默认使用英文。
- 断言验证真实可观察行为，包括返回值、状态变化、领域错误、事件、副作用和持久化结果；
  不只验证测试输入的布尔取反、常量比较或测试辅助函数自身行为。
- 时间、随机数、ID 和外部响应等不稳定依赖必须固定、注入或使用测试框架替换。
- 边界规则覆盖边界值本身和边界两侧；事务、唯一约束和并发安全存在风险时增加集成测试。
- 测试不得复制生产代码中的业务常量；通过公开行为验证规则，或从正式公共定义导入稳定常量。
- 测试报告和覆盖率报告只按用户需要手动导出，不默认生成或提交报告文件。

## AI-TEST-007

- **Who**：处理 `<组件 test>` 指令的组件测试 Agent。
- **When**：前置条件满足并准备执行组件测试阶段任务时。
- **Where**：当前组件测试目录与允许读取的设计和源码。
- **What**：提供“执行步骤”功能；具体规则、格式和约束如下。
- **Why**：确保组件测试与稳定用例编号、测试层级和文件边界一致。

1. 从 `docs/system/system.md` 组件清单的当前组件表格行解析应用目录和设计目录，并读取其开发环境端口、访问地址和接口文档。
2. 读取需求、系统规范、当前组件设计、生产源码和现有测试，不读取部署文件。
3. 从 `component.md` 的完整文件树读取计划的测试目录、测试文件、fixture、支持代码和配置；
   测试任务按该结构实现，不自行建立另一套测试目录约定。
4. 如果任务需要的测试层级或稳定测试文件未在组件设计中规划，停止对应部分并说明应切换
   `<组件>` 补充目录设计，不在测试阶段修改设计文档。
5. 覆盖任务适用的正常、失败、边界、权限和回归场景。
6. 静态检查测试导入、Fixture、Mock、断言和目录是否符合设计。
7. 按 `testing.md` 的局部执行命令先运行本次受影响测试；失败时保留失败证据并判断是测试缺陷、
   生产代码缺陷还是环境阻塞，不通过降低断言掩盖失败。
8. 受影响测试通过后执行 `testing.md` 记录的当前组件全部测试命令；环境或依赖不满足时记录阻塞原因和
   未执行范围，不虚构结果。
9. 完成时列出实际执行命令，并分别报告通过、失败、跳过和未执行的测试范围。
