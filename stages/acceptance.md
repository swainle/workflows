## AI-ACCEPTANCE-006

- **Who**：处理 `[test]` 指令的全局验收 Agent。
- **When**：需要处理“验收规则”时。
- **Where**：`test/acceptance/**` 与允许读取的前置事实。
- **What**：提供“验收规则”功能；具体规则、格式和约束如下。
- **Why**：确保跨组件验收直接验证需求和用户可观察结果。

`````md
- Requirement TC 是验收测试的稳定用例 ID；测试代码中的用例描述使用
  “`<REQ-三位编号-TC-三位序号> <Scenario 名称>`”，不创建第二套验收编号。
- 每个验收测试直接引用一个 TC Scenario 或 Scenario Outline，并验证其唯一归属的 AC；测试实现不合并
  多个 TC。Scenario Outline 的 Examples 行是同一 TC 的数据变体，可由测试运行器展开执行。
- 使用 TC 的 Given、When、Then 作为场景步骤，以关联 BP 的参与者、组件顺序、成功和失败结果
  作为跨组件边界；BP 不重新定义 BR，业务判断仍以关联需求项为准。
- 从真实 HTTP、UI、异步消息或 RPC 入口执行，验证用户可观察结果、跨组件状态和必要副作用；
  不调用私有方法或绕过正式入口直接拼装最终状态。
- 只维护必须跨组件或从系统入口验证的验收场景；Domain、Application、Repository、Adapter、
  单组件接口和 Schema 兼容性继续由 `[<组件> test]` 负责。
- 复用组件已提供的 fixture、测试支持和公开测试入口；不得在全局测试中复制业务规则、组件 Mock
  体系或机器可读契约 Schema。
- 每个测试独立建立并清理自己的数据，不依赖执行顺序；时间、随机数、ID 和外部响应必须可控。
- 验收失败必须保留原断言，如实报告实际结果；不得降低断言、改写 TC 或修改设计来制造通过。
`````

- **Who**：处理 `[test]` 指令的全局验收 Agent。

- **Where**：`test/acceptance/**` 与允许读取的前置事实。
- **What**：提供“执行规则”功能；具体规则、格式和约束如下。
- **Why**：确保跨组件验收直接验证需求和用户可观察结果。

`````md
- `[test]` 与 `[<组件> test]` 不同：全局阶段必须执行本次任务相关的验收测试命令，并如实报告
  通过、失败和未执行；环境不满足时不得声称通过。
- 只使用项目真实存在的命令和隔离的非生产环境；未配置全局验收命令时可以直接使用现有测试

- 先执行新增或修改的单个 TC，再执行受影响 BP 的相关验收测试；除非用户明确要求，不运行无关
  的全量测试、覆盖率、Lint 或构建。
- 不自动导出报告、覆盖率或执行日志；用户明确要求时只使用测试工具的临时或指定导出能力，
  不把结果写入 `docs/**`。
`````

## AI-ACCEPTANCE-008

- **Who**：处理 `[test]` 指令的全局验收 Agent。
- **When**：需要处理“执行步骤”时。
- **Where**：`test/acceptance/**` 与允许读取的前置事实。
- **What**：提供“执行步骤”功能；具体规则、格式和约束如下。
- **Why**：确保跨组件验收直接验证需求和用户可观察结果。

`````md
1. 从相关需求目录读取 AC、TC 及其 FR、BR、PERM 引用，从 `docs/system/process.md` 读取关联 BP。
2. 读取 C2 中参与组件的应用和设计目录，再读取相关组件设计、生产入口、组件测试及现有验收测试。
3. 建立“TC → AC → BP → 入口 → 可观察结果”的映射；缺失或冲突时按“越界处理”停止对应部分。
4. 只在 `test/acceptance/**` 中增量实现用户要求的跨组件验收测试及必要支持代码。
5. 静态检查测试入口、数据隔离、断言和引用，再执行本次修改的单个 TC 和受影响 BP 的相关测试。
6. 完成时列出已执行命令及通过、失败、跳过和未执行结果，不生成验收过程文档或默认报告。
`````
