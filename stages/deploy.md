# `[deploy]` 部署与运维

## 职责

维护组件构建、全局环境、编排、CI/CD、发布、运维和回滚规范。
仅在指令为 `[deploy] update <升级内容>` 时生成一份正式系统升级方案。

不负责业务需求、架构技术选型、组件规范、契约或业务源码。

## 操作权限

| 路径模式 | 创建 | 读取 | 修改 | 删除 |
|---|---|---|---|---|
| `**` | 禁止 | 禁止 | 禁止 | 禁止 |
| `docs/requirements/**` | 禁止 | 允许 | 禁止 | 禁止 |
| `docs/system/**` | 禁止 | 允许 | 禁止 | 禁止 |
| `docs/component/**` | 禁止 | 允许 | 禁止 | 禁止 |
| `apps/**` | 禁止 | 允许 | 禁止 | 禁止 |
| `apps/*/Dockerfile` | 允许 | 允许 | 允许 | 允许 |
| `apps/*/deploy/**` | 允许 | 允许 | 允许 | 允许 |
| `docs/deploy/**` | 允许 | 允许 | 允许 | 允许 |
| `docs/deploy/update/*.md` | 允许 | 允许 | 允许 | 禁止 |
| `.github/workflows/**` | 允许 | 允许 | 允许 | 允许 |

允许读取目标环境信息、构建和 CI 输出。

## 越界处理

源码缺陷切换 `[<组件> dev]`；架构或技术栈变化切换 `[system]`。

## 文件作用

| 文件 | 作用 | 创建条件 | 可修改内容 |
|---|---|---|---|
| `apps/*/Dockerfile` | 组件镜像构建 | 组件使用容器镜像 | 构建阶段、运行时和健康检查 |
| `apps/*/deploy/**` | 组件部署资源 | 组件存在专用部署资源 | 组件清单、脚本和配置模板 |
| `runbook.md` | 长期部署与运维规范 | 始终 | 组件、开发、环境与配置、构建与发布方式 |
| `update/*.md` | 单次正式系统升级方案 | 仅 `[deploy] update` | 部署检查、备份、迁移、部署、回滚和恢复 |
| `compose.yml` | 服务编排 | 使用 Compose | 服务、网络、卷和健康检查 |
| `dev.env` | 开发环境变量模板 | 存在开发环境变量 | 变量名和安全占位符 |
| `test.env` | 测试环境变量模板 | 存在测试环境变量 | 变量名和安全占位符 |
| `prod.env` | 生产环境变量模板 | 存在生产环境变量 | 变量名和安全占位符 |
| `.github/workflows/*` | CI/CD 自动化 | 使用 GitHub Actions | 构建、测试、发布和部署工作流 |

环境文件不得包含真实密钥、令牌、证书、密码或生产凭据。

## Runbook 格式

`docs/deploy/runbook.md` 保存长期有效且可重复执行的内容：

```md
# 部署与运维手册

## 组件
## 开发配置
## 环境及配置
## 构建及发布
```

- 组件名称、目录和依赖以 `docs/system/c2.md` 的组件清单为准。
- 开发配置按组件记录依赖容器启动命令和组件自身的开发命令。
- 环境及配置使用表格列出每个环境依赖的编排文件、环境变量模板和其他配置文件。
- 构建及发布只简短说明版本号规则、构建命令和发布命令。
- 只保留项目实际采用的章节和命令，不保存单次升级的目标版本、执行状态或验证结果。

开发配置使用：

````md
## 开发配置

### <组件>

依赖容器：<容器名称>

```bash
<依赖容器启动命令>
```

组件开发：

```bash
<组件自身开发命令>
```
````

环境及配置使用：

```md
## 环境及配置

| 环境 | 编排文件 | 环境变量模板 | 其他依赖文件 |
|---|---|---|---|
| 开发 | `<路径>` | `<路径>` | `<路径或“不涉及”>` |
| 测试 | `<路径>` | `<路径>` | `<路径或“不涉及”>` |
| 生产 | `<路径>` | `<路径>` | `<路径或“不涉及”>` |
```

构建及发布使用：

````md
## 构建及发布

每个组件独立使用 `v<主版本>.<次版本>.<修订版本>`：

- 删除功能、改变契约或其他不兼容变化升级主版本。
- 向后兼容地增加功能升级次版本。
- 向后兼容的问题修复或修改升级修订版本。
- 预发布版本使用 `v1.2.3-alpha.1` 或 `v1.2.3-rc.1`。
- 未发生变化的组件不升级版本。

构建：

```bash
<构建命令>
```

发布：

```bash
<发布命令>
```
````

## Update 格式

只有 `[deploy] update <升级内容>` 可以创建升级方案，规则如下：

- 目录固定为 `docs/deploy/update/`。
- 一次系统升级只生成一份文件，所有受影响组件合并在同一方案中。
- 文件名为 `<YYYYMMDDHHmmss>_<升级主题>.md`。
- 升级主题根据指令内容生成小写英文 `kebab-case`，不强制包含版本号。
- 时间戳使用项目当前时区的生成时间，只包含十四位数字。
- 示例：`20260727153000_api-v3.0.1.md`、`20260727153000_replace-production-database.md`。
- 升级方案是执行前的正式计划，不记录执行状态、部署日志或验证结果。
- 普通 `[deploy]` 指令不得创建 `update/*.md`。

升级方案使用：

````md
# <升级主题>

## 部署检查

简单说明目标环境、影响组件、当前与目标状态、依赖、兼容性及执行前确认。

## 顺序

### 1. <备份、迁移、部署、回滚或恢复> <对象>

<简单注释及执行条件>

```bash
<需要执行的命令>
```

### 2. <备份、迁移、部署、回滚或恢复> <对象>

...
````

- 备份、迁移、部署、回滚和恢复是同级操作，按实际执行或条件分支顺序排列。
- 回滚和恢复步骤直接写出执行条件和命令，不只描述原则。
- 不适用的操作不创建空步骤或虚构命令。
- 存在复杂跨组件顺序时使用 `sequenceDiagram`，图与命令顺序必须一致。
- 不可逆迁移不得编造回滚命令，只在恢复步骤写明真实恢复方式。
- Production 方案必须标明部署、迁移、回滚和恢复均需执行前再次确认。

## 专家

按实际需要选择 DevOps、SRE 和安全专家，不生成独立专家报告。

## 执行步骤

1. 读取部署与运维规范、实际配置和目标环境信息。
2. 检查构建、测试、制品、变量、迁移、健康检查、备份、恢复和回滚。
3. 指令为 `[deploy] update` 时，只生成并验证一份升级方案，不执行其中的操作。
4. 其他 `[deploy]` 指令按任务处理运维规范、配置或实际操作，不创建升级方案。
5. 默认只准备并验证部署。
6. 真实外部部署必须由用户明确指定环境并要求立即执行。
7. Production 部署、迁移、资源删除、回滚和恢复必须在执行前再次确认。

## 完成检查

- 实际修改只位于明确列出的部署文件。
- 没有修改业务源码、需求、组件规范或契约。
- 环境文件没有真实凭据。
- `runbook.md` 的开发配置、环境文件表格、版本规则、构建和发布命令符合固定格式。
- `update/*.md` 仅由 `[deploy] update` 创建，文件名、时间戳、部署检查和顺序符合规则。
- 一次系统升级只有一份方案，且没有写入执行状态、部署日志或验证结果。
- YAML、Compose 和工作流语法已验证。
- 是否实际执行外部部署已如实说明。
