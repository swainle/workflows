## AI-DEPLOY-006

- **Who**：处理 `[deploy]` 指令的部署与运维 Agent。
- **When**：需要处理“Runbook 格式”时。
- **Where**：允许维护的组件部署资源、`deploy/**` 与 CI/CD 文件。
- **What**：提供“Runbook 格式”功能；具体规则、格式和约束如下。
- **Why**：确保部署操作可复现、可验证、可恢复且高风险副作用受控。

`````md
全局部署文件统一位于项目根目录的 `deploy/`；`apps/*/deploy/**` 仅保存组件专属部署资源。

`deploy/runbook.md` 保存长期有效且可重复执行的内容：

```md
# 部署与运维手册

## 组件
## 开发配置
## 环境及配置
## 构建及发布
```

- 组件名称、目录和依赖以 `docs/system/c2.md` 的组件清单为准。
- 开发配置按组件记录环境准备、依赖基础设施启动、首次初始化和组件自身的开发命令。
- 环境及配置使用表格列出每个环境依赖的编排文件、环境变量模板和其他配置文件。
- 构建及发布只简短说明版本号规则、构建命令和发布命令。
- 只保留项目实际采用的章节和命令，不保存单次升级的目标版本、执行状态或验证结果。

开发配置使用：

````md
## 开发配置

### <组件>

依赖 <基础设施名称列表>。

```bash
cd deploy

# 准备环境变量
cp dev.env <组件应用目录相对deploy的路径>/.env
cp dev.env .env

# 拉起基础设施
docker compose up -d <依赖服务名>

# 初始化（仅首次启动）
docker compose up -d <初始化服务名>

# 启动组件
pnpm --dir <组件应用目录相对deploy的路径> dev
```
````

- `[deploy] <组件>` 只新增或更新该组件的 `### <组件>`，不改写其他组件的开发配置。
- 组件名、应用目录和基础设施依赖从 `docs/system/c2.md` 读取，不根据名称猜测路径或服务。
- 命令统一从仓库根执行并先进入 `deploy/`；因此 Compose 使用默认的
  `.env` 和 `compose.yml`，不重复传递 `--env-file` 或 `-f`。
- 先将 `dev.env` 复制为 `deploy/.env` 和组件应用目录的 `.env`；
  Runbook 只提供命令，不自动执行或覆盖本地文件。
- JavaScript 和 TypeScript 组件默认使用 `pnpm`；项目明确采用其他包管理器时使用项目实际命令。
- 日常启动只拉起当前组件实际依赖的服务，不使用无目标的 `docker compose up -d`。
- 需要显式初始化时使用独立的一次性 Compose 服务，名称优先为 `<基础设施>-init`，
  并在 Runbook 中标注“仅首次启动”；没有初始化步骤时省略该命令和注释。
- 初始化服务在 `compose.yml` 中依赖目标服务健康、使用 `restart: "no"`，并引用
  `deploy/init/<基础设施>/` 中实际需要的脚本或配置。基础设施原生初始化机制足够时不额外创建 init 服务。
- Runbook 不复制 Compose 已维护的镜像、端口、网络、卷、健康检查或初始化实现。
- 破坏性重置、删除卷或清空数据不属于首次初始化，不写入普通开发配置。
`````

## AI-DEPLOY-007

- **Who**：处理 `[deploy]` 指令的部署与运维 Agent。
- **When**：需要处理“Update 格式”时。
- **Where**：允许维护的组件部署资源、`deploy/**` 与 CI/CD 文件。
- **What**：提供“Update 格式”功能；具体规则、格式和约束如下。
- **Why**：确保部署操作可复现、可验证、可恢复且高风险副作用受控。

`````md
只有 `[deploy] update <升级内容>` 可以创建升级方案，规则如下：

- 目录固定为 `deploy/update/`。
- 一次系统升级只生成一份文件，所有受影响组件合并在同一方案中。
- 文件名为 `<YYYYMMDDHHmmss>_<升级主题>.md`。
- 升级主题根据指令内容生成小写英文 `kebab-case`，不强制包含版本号。
- 时间戳使用项目当前时区的生成时间，只包含十四位数字。
- 示例：`20260727153000_api-v3.0.1.md`、`20260727153000_replace-production-database.md`。
- 升级方案是执行前的正式计划，不记录执行状态、部署日志或验证结果。
- 普通 `[deploy]` 指令不得创建 `update/*.md`。

升级方案使用：

````md
# <升级主题>

## 部署检查

简单说明目标环境、影响组件、当前与目标状态、依赖、兼容性及执行前确认。

## 顺序

### 1. <备份、迁移、部署、回滚或恢复> <对象>

<简单注释及执行条件>

```bash
<需要执行的命令>
```

### 2. <备份、迁移、部署、回滚或恢复> <对象>

...
````

- 备份、迁移、部署、回滚和恢复是同级操作，按实际执行或条件分支顺序排列。
- 回滚和恢复步骤直接写出执行条件和命令，不只描述原则。
- 不适用的操作不创建空步骤或虚构命令。
- 存在复杂跨组件顺序时使用 `sequenceDiagram`，图与命令顺序必须一致。
- 不可逆迁移不得编造回滚命令，只在恢复步骤写明真实恢复方式。
- Production 方案必须标明部署、迁移、回滚和恢复均需执行前再次确认。
`````
