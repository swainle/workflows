# AI 项目工作流

本文件是尖括号指令的全局入口和阶段路由器，通常由
`docs/workflows/install.mjs` 安装到宿主项目根目录。

## AI-001

- **Who**：所有处理本工作流指令的 Agent。
- **When**：识别出受本工作流管理的尖括号指令时。
- **Where**：宿主项目根 `AGENTS.md` 的托管区块与工作流入口。
- **What**：提供“全局规则”功能；具体规则、格式和约束如下。
- **Why**：确保全局行为可预测、阶段边界一致且操作结果可验证。

- 本文件的阶段路由和消息结尾控制只约束以本文所定义尖括号指令开头的任务。
- 宿主项目在托管区块之外的项目规则继续有效，并在冲突时优先。
- 当前本地磁盘是事实，不用 Git 历史覆盖当前文件。
- 除 `<deploy update>` 生成的正式系统升级方案外，不创建工作流状态、讨论、开发、部署或验证记录。
- 保留用户已有修改，不重置、不清理、不顺手修改无关内容。
- 本地文件的创建、读取、修改和删除只按当前阶段的操作权限表执行。
- 每个阶段的操作权限表必须以 `**` 全部禁止作为默认规则；只有表中更具体的路径可以开放操作。
- 阶段按“需求 → system → 组件设计 → dev → 组件 test → 全局 test → deploy”串行；当前阶段只读前置阶段和本阶段文件，只增删改本阶段文件。
- 路径必须在授权目录内，不包含 `..`，不得通过符号链接跳出范围。

## AI-002

- **Who**：所有处理本工作流指令的 Agent。
- **When**：生成对话回复、正式文档、测试描述、用户提示、日志字段或代码注释时。
- **Where**：宿主项目根 `AGENTS.md` 的托管区块与工作流入口。
- **What**：提供“语言规则”功能；具体规则、格式和约束如下。
- **Why**：确保全局行为可预测、阶段边界一致且操作结果可验证。

- 对话回复、正式文档、测试用例描述和必要的代码注释默认使用中文。
- 类名、函数名、变量名、文件名、包名、环境变量、HTTP 字段、数据库字段和协议名称
  遵循项目既有约定，默认使用英文。
- OpenAPI、AsyncAPI、SQL、命令行和第三方 API 的固定名称不得为了中文化而改写。
- 面向用户的提示和错误信息按产品语言规范使用中文；日志中的稳定事件名和机器可解析字段使用英文。
- 中文注释说明设计原因、业务约束和风险，不逐行翻译代码。

## AI-003

- **Who**：所有处理本工作流指令的 Agent。
- **When**：已识别尖括号工作流指令，且去除末尾空白后的最后一个字符属于受支持控制符时。
- **Where**：宿主项目根 `AGENTS.md` 的托管区块与工作流入口。
- **What**：提供“消息结尾控制”功能；具体规则、格式和约束如下。
- **Why**：确保全局行为可预测、阶段边界一致且操作结果可验证。

去除消息末尾空白后，按最后一个字符控制当前消息的执行方式；中英文符号等价：

| 结尾 | 执行方式 |
|---|---|
| `?` 或 `？` | 只回答问题，不修改文件 |
| `!` 或 `！` | 遵循适用规范修改和验证文件，提交并推送产生的修改 |
| `,` 或 `，` | 需求尚未完成，不修改文件；一次提出一个最影响结果的问题，直至完全理解需求 |
| `.` 或 `。` | 允许遵循适用规范修改和验证文件，不自动提交或推送 |

- 没有以上结尾时按现有任务规则处理。
- 即使以 `!`、`！`、`.` 或 `。` 结尾，存在会产生不同结果的关键歧义时仍先询问。
- Production 部署、迁移、资源删除、回滚等要求再次确认的高风险操作不因结尾符号跳过确认。

## AI-004

- **Who**：所有处理本工作流指令的 Agent。
- **When**：识别出受管尖括号指令，或用户明确要求安装、更新或切换工作流分支时。
- **Where**：宿主项目根 `AGENTS.md` 的托管区块与工作流入口。
- **What**：校验当前加载的工作流代码 SHA，并安装或刷新宿主项目使用的提示词。
- **Why**：避免宿主已经拉取新工作流代码后，Agent 继续使用旧托管提示词或阶段规则。

每个受管尖括号指令都必须先通过版本门禁；门禁完成前只允许读取宿主根 `AGENTS.md`、读取工作流 Git 元数据，并在版本不一致时运行下述本地安装命令，禁止其他项目文件操作、项目命令、外部系统访问或澄清问题。

门禁依次取得并比较三个完整 SHA：当前任务最近采用的托管提示词 SHA、磁盘中宿主根 `AGENTS.md` 托管区块的 `workflows-revision`、本地工作流 HEAD：

```bash
git -C docs/workflows rev-parse HEAD
```

托管区块使用 `<!-- workflows-revision: <完整 SHA> -->` 记录版本，按以下规则处理：

- 三个 SHA 一致时通过门禁，不访问远端。
- 磁盘 SHA 与本地 HEAD 不一致时执行 `node docs/workflows/install.mjs --workflows-updated`，只使用已经拉取到本地的代码重新安装托管区块。
- 当前任务采用的 SHA 与刷新后的磁盘 SHA 不一致时，完整重读宿主根 `AGENTS.md`，以新托管区块替换本次指令采用的旧提示词，再重新解析当前指令并读取其必需的阶段和模式提示词。
- 刷新或重读后重新取得三个 SHA；只有三者一致才允许继续，同一条指令最多刷新一次。SHA 缺失、不是完整值、检查失败或再次不一致时停止，不使用可能过期的提示词执行当前指令。
- 通过门禁后必须按 AI-011 回显完整 SHA 和状态；没有版本回显的指令不得执行。

在宿主项目根目录执行：

```bash
node docs/workflows/install.mjs
```

安装器把 `templates/AGENTS.template.md` 同步到宿主根 `AGENTS.md` 的
`<!-- workflows:begin -->` 与 `<!-- workflows:end -->` 托管区块，保留区块外的宿主规则。不要手动修改托管区块。
托管区块中的 `workflows-revision` 由安装器使用当前代码的完整 Git SHA 生成，不手动修改。
不传 `--branch` 时对子模块当前检出的分支执行 `git pull --ff-only` 后安装；
需要切换并更新分支时使用 `node docs/workflows/install.mjs --branch <分支>`。
子模块处于 detached HEAD（例如直接检出 Tag）时必须指定分支。

阶段文件保留在 `docs/workflows/stages/`，安装器会检查路由引用的阶段文件是否存在。

## AI-005

- **Who**：所有处理本工作流指令的 Agent。
- **When**：用户消息以尖括号指令开头，需要确定目标阶段、组件、模式或部署子命令时。
- **Where**：宿主项目根 `AGENTS.md` 的托管区块与工作流入口。
- **What**：提供“指令语法”功能；具体规则、格式和约束如下。
- **Why**：确保全局行为可预测、阶段边界一致且操作结果可验证。

受管理指令必须以一对实际的尖括号字符开头；从消息开头读取至第一个 `>` 作为唯一指令头，
其后的文本作为任务参数。本文语法示例中，指令开头的 `<...>` 是必须原样输入的结构；
其余 `<组件>`、`<目标文件>` 等名称表示需要按实际情况替换的占位符。

指令头按以下优先级解析：

1. 纯数字：GitHub Issue 需求，例如 `<12>`；
2. 保留全局指令：`<system>`、`<test>`、`<deploy>`、`<deploy update>`；
3. `<组件名 deploy>`：目标组件的开发基础设施；
4. `<组件名 dev>` 或 `<组件名 test>`：目标组件的开发或测试阶段；
5. `<组件名>`：目标组件的设计阶段。

保留指令优先于组件名。消息以 `<` 开头但指令头格式错误、目标组件未登记或子命令未知时，
停止并说明原因；普通自然语言任务不套用本工作流，按宿主项目规则处理。

### GitHub Issue 需求

> - 根据实际情况修改

```text
<Issue编号> <可选补充要求>
```

示例：

> - 根据实际情况修改

```text
<1> 初始化预约系统
<12> 增加预约改期
```

`<1>` 固定对应 GitHub Issue `#1`。编号不足三位时左侧补零，达到或超过三位时保留完整编号：

> - 根据实际情况修改

```text
Issue #1   → docs/requirements/REQ-001-<slug>/
Issue #12  → docs/requirements/REQ-012-<slug>/
Issue #123 → docs/requirements/REQ-123-<slug>/
Issue #1000 → docs/requirements/REQ-1000-<slug>/
```

### 组件任务

> - 根据实际情况修改

```text
<组件> <规范任务>
<组件> frontend <前端设计任务>
<组件> backend <后端设计任务>
<组件> opt <目标文件> <意见>
<组件> frontend opt <目标文件> <意见>
<组件> backend opt <目标文件> <意见>
<组件 dev> <开发任务>
<组件 test> <测试任务>
<组件 deploy> <开发基础设施任务>
```

示例：

> - 根据实际情况修改

```text
<web> 讨论预约页面规范
<web> frontend 设计预约前端
<booking-api> backend 设计预约后端
<booking-api> opt component.md 补充组件职责
<web> frontend opt layout.md 调整页面布局边界
<booking-api> backend opt domain.md 调整聚合边界
<web dev> 调整登录按钮圆角
<web test> 验证登录页面
<booking-api> 讨论预约接口
<booking-api dev> 实现创建预约接口
<booking-api deploy> 更新开发环境配置
```

`<组件>` 必须对应 `docs/system/system.md` 组件清单中已声明的组件。
组件任务从该组件表格行“说明”列的固定字段“应用：`<路径>`；设计：`<路径>`”解析组件应用目录和组件设计目录，
不根据组件名称猜测路径。
`frontend` 和 `backend` 只能作为 `<组件>` 指令头后的第一个任务词，用于启用
`stages/component.md` 中对应的完整组件设计模式；它们不是组件名或独立阶段，
不得写入指令头，也不适用于 `dev`、`test` 或 `deploy` 任务。组件设计的 `opt` 可直接跟在指令头后，或紧跟
`frontend`、`backend`，表示按当前组件设计顺序或所选模板依赖顺序创建或更新一个文件；
具体读取和修改范围由 `stages/component.md` 定义。其他指令的 `opt` 统一遵循 AI-015。
组件类型与设计模式明显冲突时停止，说明应使用 `<system>` 调整组件划分。
不得在组件任务中自行创造组件；新增或拆分组件先使用 `<system>` 确认全局架构。
保留目标：

> - 根据实际情况修改

```text
<system>         全局架构、技术和开发约定
<test>           跨组件验收测试及执行
<deploy>         组件构建、全局编排、CI/CD、发布和回滚
<组件 deploy>   当前组件的开发基础设施、初始化和启动说明
```

`<组件 deploy>` 中的组件名必须精确匹配 `docs/system/system.md` 组件清单；
该指令按 `stages/deploy.md` 更新组件开发配置，不是生产部署，也不创建升级方案。

全局验收测试使用：

> - 根据实际情况修改

```text
<test> <验收任务>
```

`<test>` 根据需求 TC、AC 和系统 BP 维护并执行 `test/acceptance/**` 中的跨组件验收测试；
它不替代 `<组件 test>` 的组件单元、集成、接口、契约或并发测试。
精确的 `<test>` 是保留的全局指令，必须优先于 `<组件>` 解析，不得把 `test` 当作组件名。

部署升级方案使用：

> - 根据实际情况修改

```text
<deploy update> <升级内容>
```

只有明确包含 `update` 的 `<deploy>` 指令才在 `deploy/update/` 生成一份系统升级方案；
其他 `<deploy>` 指令处理构建、发布、部署、检查、回滚和恢复等运维任务，不生成升级方案。

## AI-006

- **Who**：所有处理本工作流指令的 Agent。
- **When**：指令语法解析成功，需要选择并加载必读阶段或模式提示词时。
- **Where**：宿主项目根 `AGENTS.md` 的托管区块与工作流入口。
- **What**：提供“阶段路由”功能；具体规则、格式和约束如下。
- **Why**：确保全局行为可预测、阶段边界一致且操作结果可验证。

识别指令后，必须在读取或修改项目文件前完整读取对应阶段文件。只读取当前任务需要的阶段文件，不读取无关阶段。
`opt` 只改变当前阶段的执行范围，不改变阶段路由；先按原指令头选择阶段，再应用 AI-015 的单文件限制。

| 指令 | 必读阶段文件 |
|---|---|
| `<编号>` | `docs/workflows/stages/requirement.md` |
| `<组件>` | `docs/workflows/stages/component.md` |
| `<组件 dev>` | `docs/workflows/stages/component-dev.md` |
| `<组件 test>` | `docs/workflows/stages/component-test.md` |
| `<test>` | `docs/workflows/stages/test.md` |
| `<system>` | `docs/workflows/stages/system.md` |
| `<deploy>`、`<组件 deploy>`、`<deploy update>` | `docs/workflows/stages/deploy.md` |

阶段文件不存在或无法完整读取时停止，不修改任何文件。

阶段文件中的操作权限表是当前任务的文件操作白名单。“职责”“文件作用”“执行步骤”和“完成检查”均为强制规则。

前端、后端、任务处理器等组件统一使用组件阶段；系统可以声明多个后端组件。

用户明确给出多个阶段时按阶段顺序分别执行，每一步只使用该阶段权限，不合并写入范围，
也不自动扩大到相关阶段或其他组件。

## AI-007

- **Who**：所有处理本工作流指令的 Agent。
- **When**：阶段路由完成后，在任何项目文件创建、读取、修改、删除、移动或重命名前。
- **Where**：宿主项目根 `AGENTS.md` 的托管区块与工作流入口。
- **What**：提供“操作权限表”功能；具体规则、格式和约束如下。
- **Why**：确保全局行为可预测、阶段边界一致且操作结果可验证。

- `*` 只匹配一个路径层级，`**` 匹配任意深度。
- 每张表的第一条规则必须是 `| ** | 禁止 | 禁止 | 禁止 | 禁止 |`，显式禁止所有目录和文件。
- 目录权限由后代路径继承。多条规则匹配时，路径越具体越优先，并按操作类型覆盖父级权限。
- 路径具体程度相同时，“禁止”优先。
- 前置阶段目录只允许读取；当前阶段目录按表格开放操作；后置阶段和无关目录由 `**` 默认规则禁止所有操作。
- 创建、读取、修改和删除相互独立，允许其中一项不隐含其他权限。
- 重命名或移动文件同时需要源路径的删除权限和目标路径的创建权限。
- 删除权限只表示当前阶段可以删除；删除重要文件仍须由用户明确要求或确认。
- 操作前解析并检查实际路径；不得使用 `..` 或符号链接绕过权限边界。

## AI-008

- **Who**：所有处理本工作流指令的 Agent。
- **When**：当前任务需要读取项目事实或多个事实来源出现不一致时。
- **Where**：宿主项目根 `AGENTS.md` 的托管区块与工作流入口。
- **What**：提供“本地事实来源”功能；具体规则、格式和约束如下。
- **Why**：确保全局行为可预测、阶段边界一致且操作结果可验证。

> - 根据实际情况修改

```text
docs/**                        需求、规范和契约
apps/**                        当前实际实现
<组件应用目录>/test/**         自动化测试实现
test/acceptance/**             跨组件验收测试实现
deploy/**                      全局部署与运维配置
Git                            文件历史
测试和 CI 输出                 执行证据
```

- 每个阶段只使用操作权限表允许读取的本地事实。
- 开发、组件测试、全局验收和部署按串行顺序读取前置阶段产物，不反向读取后置阶段文件。
- 不通过修改规范掩盖实现问题，也不通过降低断言掩盖测试失败。
- 单次讨论、开发过程、测试输出和部署日志不写入 `docs/**`。

## AI-009

- **Who**：所有处理本工作流指令的 Agent。
- **When**：需求、系统或组件设计任务存在会改变结果的歧义、冲突或关键缺失时。
- **Where**：宿主项目根 `AGENTS.md` 的托管区块与工作流入口。
- **What**：提供“对话确认规则”功能；具体规则、格式和约束如下。
- **Why**：确保全局行为可预测、阶段边界一致且操作结果可验证。

适用于 `<编号>`、`<组件>` 和 `<system>`：

1. 只读取当前阶段操作权限表允许的 Issue 和前置阶段上下文。
2. 自动判断是否存在无法理解、相互冲突、关键缺失或会产生不同结果的合理选择。
3. 没有实质不确定项时不为形式提问。
4. 存在不确定项时，一次只询问一个最影响结果的问题，并说明影响。
5. 问题解决后，简单输出对目标、范围、关键行为、不包含内容和影响文件类型的理解。
6. 请求用户最终确认。
7. 得到明确确认后才修改规范文件。
8. 未确认内容不写入仓库；确认结果直接写入正式规范，不创建讨论记录。

`<组件 dev>` 还必须先按 `stages/component-dev.md` 完成组件设计入口读取、实现映射和技术
可行性检查；任何影响行为、契约、安全、数据、兼容性或文件结构的未确认项都必须先提问，
未确认项清零后才能修改代码。明确且局部且已被设计唯一确定的机械实现细节不为形式提问。
测试和部署任务存在歧义、外部副作用或范围扩大时再确认。

## AI-010

- **Who**：所有处理本工作流指令的 Agent。
- **When**：正式 Markdown 产物确实需要表达复杂关系、顺序、状态或数据结构时。

## AI-011

- **Who**：解析并准备执行受本工作流管理指令的主 Agent。
- **When**：指令解析完成且必读阶段、模式提示词已经完整加载后，任何实质操作开始前。
- **Where**：当前指令的第一条用户可见回复，以及根提示词、阶段提示词和模式提示词的规则编号。
- **What**：提供“命中规则回显”功能；具体规则、格式和约束如下。
- **Why**：让用户在执行前确认 Agent 实际采用了哪些规则，便于发现错误路由或遗漏约束。

对受本工作流管理的尖括号指令执行以下规则：

1. 先解析指令、结尾控制符、目标阶段和可选模式，再完整读取路由要求的阶段及模式提示词。
2. 提示词读取不属于实质操作。完成读取后，以“当前指令、已解析参数、当前任务状态”为输入，
   逐条判断根提示词、目标阶段提示词和已启用模式提示词的 `When` 是否为真。
3. 只把 `When` 在当前时点为真的规则视为命中；仅因文件已加载、后续可能使用或同属一个阶段，
   不得判定为命中。`When` 无法得到唯一真假结果时，先修正规则或请求澄清，不猜测。
4. 在读取或修改项目业务文件、运行项目命令、调用外部系统、提出澄清问题或执行其他任务动作前，
   第一条用户可见回复必须先输出版本门禁结果，再输出命中规则：

> - 根据实际情况修改

```text
提示词版本：<完整 SHA>（一致）
命中规则：AI-001、AI-004、AI-005、AI-006、AI-007、AI-011、AI-TEST-001、AI-TEST-002
```

   本次发生刷新时，版本行改为 `提示词版本：<新完整 SHA>（已从 <旧完整 SHA> 刷新）`。版本行必须使用本次门禁实际读取的 SHA，不缩写、不猜测。
5. 版本门禁未通过、版本行没有输出或 SHA 与门禁结果不一致时停止；只列真实存在且当前命中的规则编号，不列未命中规则、未来阶段规则或纯占位符，不虚构编号。
6. 编号按根提示词、阶段提示词、模式提示词的顺序排列；同一编号只列一次，不使用编号范围代替逐条判断。
7. 回显是执行前快照。同一条用户指令只回显一次；任务进行中后续才满足的完成类规则不补发回显。
8. 用户提出新的受管理指令时重新解析并计算；未命中本工作流的普通自然语言任务不强制回显。

## AI-012

- **Who**：所有处理本工作流指令的 Agent。
- **When**：当前任务准备结束并生成最终回复前。
- **Where**：宿主项目根 `AGENTS.md` 的托管区块与工作流入口。
- **What**：提供“完成标准”功能；具体规则、格式和约束如下。
- **Why**：确保全局行为可预测、阶段边界一致且操作结果可验证。

完成前：

1. 逐个检查实际文件操作是否符合阶段操作权限表。
2. 检查没有覆盖无关用户修改、密钥或真实凭据。
3. 执行阶段文件的“完成检查”。
4. 运行与修改风险相称的现有验证命令。
5. 如实区分通过、失败、跳过和未执行。

最终回复只包含：

- 完成内容；
- 修改文件；
- 验证命令与结果；
- 功能点变更（适用时）；
- 未解决问题或剩余风险。

## AI-013

- **Who**：所有修改本工作流提示词功能点的 Agent。
- **When**：当前任务新增、删除或修改了一个或多个 `## AI-*` 功能块。
- **Where**：当前任务的最终回复与本次实际变更的提示词功能编号。
- **What**：提供“功能点变更回显”功能；具体规则、格式和约束如下。
- **Why**：让用户直接看到本次调整影响了哪些稳定功能，而不必从文件差异中反查编号。

最终回复必须为每个实际增删改的功能点输出一行：

> - 根据实际情况修改

```text
- **AI-BACKEND-001**: 修改 Backend 设计模式选择规则
```

- 使用功能块原有或新增的完整编号；删除功能点时仍使用被删除的原编号。
- 冒号后用一句话说明“新增、删除或修改”了什么，不重复文件名、验证结果或实现过程。
- 多个功能点按提示词文件及编号顺序逐行输出；没有功能点变更时不输出。

## AI-014

- **Who**：所有准备优化、新增、删除或修改本工作流提示词功能点的 Agent。
- **When**：功能点变更方案尚未确定，准备修改任意 `## AI-*` 功能块前。
- **Where**：仓库内全部根提示词、阶段提示词和模式提示词功能块。
- **What**：提供“功能复用审查”功能；具体规则、格式和约束如下。
- **Why**：优先增强已有职责，避免重复规则、编号膨胀和相互冲突的功能定义。

修改前必须：

1. 根据目标行为及其 `Who`、`When`、`Where`、`What`、`Why`，搜索全部 `## AI-*` 功能块，不只搜索预计修改的文件。
2. 已有功能完整覆盖目标时，只优化该功能；部分覆盖时，优先在职责最接近的功能上扩展或收敛，并保留原编号。
3. 多个功能重复或冲突时，合并到唯一职责归属；删除功能前确认其仍需保留的规则和引用已经迁移。
4. 只有没有已有功能可以合理承载，并且目标具有可独立维护的 `When` 与职责时，才新增下一个连续编号。
5. 修改范围只包含复用判断所需的功能及其文档和校验，不顺手调整无关规则。

## AI-015

- **Who**：处理任意受管理指令单文件优化任务的 Agent。
- **When**：指令任务参数以 `opt` 开头，或组件设计模式名后紧跟 `opt`，并指定一个目标文件时。
- **Where**：原指令路由的阶段、该阶段原本允许创建或修改的一个目标文件及完成优化所必需的前置事实。
- **What**：提供“通用单文件优化”功能；具体规则、格式和约束如下。
- **Why**：让所有指令使用一致的最小修改方式创建或更新目标文件，同时保持原阶段边界和权限不变。

所有受管理指令都支持以下形式：

> - 根据实际情况修改

```text
<编号> opt <目标文件> <可选意见>
<system> opt <目标文件> <可选意见>
<组件> opt <目标文件> <可选意见>
<组件> frontend opt <目标文件> <可选意见>
<组件> backend opt <目标文件> <可选意见>
<组件 dev> opt <目标文件> <可选意见>
<组件 test> opt <目标文件> <可选意见>
<test> opt <目标文件> <可选意见>
<deploy> opt <目标文件> <可选意见>
<组件 deploy> opt <目标文件> <可选意见>
<deploy update> opt <目标文件> <可选意见>
```

1. 先按不含 `opt`、目标文件和意见的原指令完成阶段路由并读取该阶段提示词；`opt` 不创建新阶段，也不跳过原阶段规则。
2. 目标文件必须唯一且不包含 `..`；文件已存在时原阶段操作权限表必须允许修改，文件不存在时必须允许创建。`opt` 不会把原本只读或禁止创建、修改的文件变为可写。
3. 读取范围只包含原阶段允许读取且理解目标文件所必需的前置事实；不得借 `opt` 扩大到后置阶段或无关目录。
4. 写入权限收窄为只允许创建或修改目标文件；目标存在时更新，不存在时创建。禁止删除、移动、重命名或顺手创建、修改关联文件，需要同步的其他文件只报告影响。
5. 阶段提示词存在更严格的专用 `opt` 规则时同时遵循，以更窄的读取、写入和依赖范围为准；组件设计使用 AI-COMPONENT-014。
6. 完成后执行目标文件适用的格式、引用、语法或最小行为校验，并列出目标文件、验证结果和未修改的后续影响。
