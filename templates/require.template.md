# Require 需求与架构模板

用于 `<doc 组件> tmp require [issue <编号>]`。不指定 Issue 时以用户任务为需求输入；
指定时读取该 Issue 并限定本次分析范围。

执行前必须完整读取：

1. `templates/require/requirements.md`
2. `templates/require/architecture.md`

## 专家团

`tmp require` 总是运行专家团，无论是否指定 Issue；成员如下：

- 产品与领域专家：评审模块、页面、FR、角色、使用环境、BR、FLOW 和业务边界。
- 架构与安全专家：评审系统边界、组件协作、契约、PERM、安全、数据和可观测性。
- 验收与质量专家：评审页面可观察状态、终端约束、可访问性、NFR、AC、TC、完整性和可验证性。

专家只读分析并返回决策、风险、建议和阻塞；主 Agent 统一分类、决策、修改与验证。

## 执行顺序

1. 完整执行需求规则的全量 FR、CRUD、关联文件和变更分类分析。
2. `CONFLICT` 或高影响专家分歧未解决时停止，不用架构设计掩盖需求冲突。
3. 以已确认需求为输入执行架构规则，检查全局设计与 FR、FLOW、NFR、PERM 和 AC 一致。
4. 只增量修改当前任务需要的需求、追溯投影和全局设计文件，最后统一更新 README 索引。

## 完成检查

- 需求分析和架构评审都已执行，没有跳过专家团或全量 FR 分析。
- Issue 只在显式指定时读取和记录；未指定时不猜测 Issue。
- 全局设计没有新增 FR 未定义的业务能力。
- 每个页面都在所属模块中映射到真实 FR，页面与功能的多对多关系没有复制或改写 FR 行为。
- 面向界面的需求已在各自事实源中覆盖页面关系、可观察状态、使用环境、可测体验约束和数据可见范围，可供 DESIGN.md 使用；没有写入颜色、字号、间距、组件结构或实现方案。
